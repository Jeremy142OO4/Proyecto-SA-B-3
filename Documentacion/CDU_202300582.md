
## Casos de Uso de Alto Nivel y Exapnadidos 

### Caso de Uso : Registrar Cliente


| Campo | Descripción |
|---|---|
| **ID Caso de Uso** | CDU-CUS-01 |
| **Nombre** | Registrar cliente |
| **Módulo al que pertenece** | Customer Service |
| **Actor Principal** | Cajero Receptor |
| **Precondiciones** | - El Cajero Receptor debe haber iniciado sesión en el sistema.<br>- El cliente debe proporcionar sus datos personales.<br>- El cliente debe proporcionar un documento de identificación y una fotografía del mismo.<br>- El cliente debe proporcionar una dirección de correo electrónico válida. |
| **Postcondiciones** | - Se crea un nuevo cliente en el sistema.<br>- Se genera un `customerId` para identificar al cliente.<br>- Se genera automáticamente un username a partir del nombre del cliente.<br>- Los datos del cliente quedan almacenados en la base de datos de Customer Service.<br>- El cliente queda pendiente de activación. |
| **Escenario Principal** | 1. El Cajero Receptor selecciona la opción **Registrar cliente**.<br>2. El sistema muestra el formulario de registro.<br>3. El Cajero Receptor ingresa el nombre completo, documento, correo, fecha de nacimiento y dirección del cliente.<br>4. El Cajero Receptor adjunta la fotografía del documento de identificación.<br>5. El sistema valida que los datos ingresados tengan un formato correcto.<br>6. El sistema valida la coherencia de la fecha de nacimiento.<br>7. El sistema genera automáticamente el username del cliente a partir de su nombre.<br>8. El sistema genera el `customerId` del cliente.<br>9. El sistema almacena la información en la base de datos de Customer Service.<br>10. El sistema informa que el cliente fue registrado correctamente. |
| **Escenario Alternativo** | **1. Datos incompletos o inválidos:** El sistema muestra los campos incorrectos y solicita su corrección.<br><br>**2. Fecha de nacimiento inválida:** El sistema rechaza el registro e informa que la fecha ingresada no es coherente.<br><br>**3. Documento o fotografía faltante:** El sistema solicita completar la información de identificación antes de continuar.<br><br>**4. Error durante el registro:** El sistema informa que no fue posible completar la operación y evita almacenar información parcial. |
| **Requerimientos** | - El sistema debe permitir registrar los datos personales del cliente.<br>- El sistema debe permitir cargar la fotografía del documento de identificación.<br>- El sistema debe validar la coherencia de la fecha de nacimiento.<br>- El sistema debe generar automáticamente el username a partir del nombre del cliente.<br>- Cada cliente debe contar con un identificador único `customerId`.<br>- La información debe almacenarse únicamente en la base de datos correspondiente a Customer Service.<br>- El registro debe contemplar manejo de errores e idempotencia para evitar registros duplicados. |



### Caso de Uso: Actualizar datos del cliente

| Campo | Descripción |
|---|---|
| **ID Caso de Uso** | CDU-CUS-03 |
| **Nombre** | Actualizar datos del cliente |
| **Módulo al que pertenece** | Customer Service |
| **Actor Principal** | Cliente |
| **Precondiciones** | - El cliente debe estar registrado en el sistema.<br>- El cliente debe haber iniciado sesión correctamente.<br>- El cliente debe encontrarse activo.<br>- El sistema debe poder identificar al cliente mediante su `customerId`. |
| **Postcondiciones** | - Los datos modificados quedan actualizados en la base de datos de Customer Service.<br>- La información anterior es reemplazada únicamente en los campos permitidos.<br>- El sistema confirma que la actualización fue realizada correctamente.<br>- No se generan registros duplicados durante la operación. |
| **Escenario Principal** | 1. El cliente inicia sesión en el sistema.<br>2. El cliente selecciona la opción **Actualizar datos**.<br>3. El sistema muestra la información actualmente registrada del cliente.<br>4. El cliente modifica los campos permitidos, como correo electrónico o dirección.<br>5. El cliente confirma los cambios realizados.<br>6. El sistema valida que los nuevos datos tengan un formato correcto.<br>7. El sistema identifica al cliente mediante su `customerId`.<br>8. El sistema actualiza la información correspondiente en la base de datos de Customer Service.<br>9. El sistema confirma que los datos fueron actualizados correctamente. |
| **Escenario Alternativo** | **1. Datos inválidos:** Si alguno de los nuevos datos no cumple con el formato establecido, el sistema muestra un mensaje de error y solicita corregirlo.<br><br>**2. Correo electrónico inválido:** Si el nuevo correo no tiene un formato válido, el sistema rechaza la modificación.<br><br>**3. Cliente no encontrado:** Si el `customerId` no corresponde a un cliente registrado, el sistema cancela la operación e informa el error.<br><br>**4. No se realizaron cambios:** Si el cliente no modifica ningún dato, el sistema mantiene la información original.<br><br>**5. Error durante la actualización:** Si ocurre un fallo durante el proceso, el sistema evita guardar información parcial y mantiene los datos anteriores. |
| **Requerimientos** | - El sistema debe permitir actualizar los datos del cliente.<br>- La actualización debe realizarse únicamente sobre la base de datos correspondiente a Customer Service.<br>- El sistema debe validar los datos antes de almacenarlos.<br>- El sistema debe identificar al cliente mediante su `customerId`.<br>- El proceso debe implementar idempotencia para evitar actualizaciones duplicadas.<br>- El sistema debe contemplar protección contra condiciones de carrera durante la actualización.<br>- El sistema debe manejar errores sin dejar información inconsistente. |

### Caso de Uso: Iniciar Sesion

| Campo | Descripción |
|---|---|
| **ID Caso de Uso** | CDU-CUS-05 |
| **Nombre** | Iniciar sesión / Autenticar usuario |
| **Módulo al que pertenece** | Customer Service |
| **Actor Principal** | Cliente |
| **Precondiciones** | - El cliente debe estar registrado en el sistema.<br>- El cliente debe contar con un username válido.<br>- El cliente debe proporcionar sus credenciales de acceso.<br>- El sistema debe tener acceso a la información necesaria para validar al usuario. |
| **Postcondiciones** | - El usuario queda autenticado correctamente en el sistema.<br>- El sistema genera un token JWT para validar la sesión del usuario.<br>- Si corresponde al primer inicio de sesión, se inicia el proceso de activación de la cuenta.<br>- El usuario puede acceder a las funcionalidades permitidas según su tipo de usuario. |
| **Escenario Principal** | 1. El cliente accede a la opción **Iniciar sesión**.<br>2. El sistema muestra el formulario de autenticación.<br>3. El cliente ingresa su username y contraseña.<br>4. El sistema valida las credenciales ingresadas.<br>5. El sistema verifica que el usuario exista en Customer Service.<br>6. Si las credenciales son correctas, el sistema genera un token JWT.<br>7. El sistema permite el acceso del cliente a las funcionalidades correspondientes.<br>8. El sistema confirma que la autenticación fue realizada correctamente. |
| **Escenario Alternativo** | **1. Credenciales incorrectas:** Si el username o contraseña son incorrectos, el sistema rechaza el acceso e informa al usuario.<br><br>**2. Usuario inexistente:** Si el usuario no se encuentra registrado, el sistema informa que las credenciales no son válidas.<br><br>**3. Primer inicio de sesión:** Si es el primer login del cuentahabiente, el sistema inicia el proceso de activación y se debe enviar un correo con un enlace para validar al usuario.<br><br>**4. Cuenta pendiente de activación:** El sistema solicita completar la validación mediante el enlace enviado al correo.<br><br>**5. Error durante la autenticación:** Si ocurre un fallo durante el proceso, el sistema rechaza temporalmente el acceso e informa al usuario. |


### Caso de Uso: Crear cuenta Bancaria

| Campo | Descripción |
|---|---|
| **ID Caso de Uso** | CDU-ACC-01 |
| **Nombre** | Crear cuenta bancaria |
| **Módulo al que pertenece** | Account Service |
| **Actor Principal** | Cajero Receptor |
| **Precondiciones** | - El Cajero Receptor debe haber iniciado sesión en el sistema.<br>- El cliente debe estar previamente registrado en el sistema.<br>- Debe existir un `customerId` asociado al cliente.<br>- Se debe seleccionar el tipo de cuenta que se desea crear: **Monetaria** o **Ahorro**. |
| **Postcondiciones** | - Se crea una nueva cuenta bancaria asociada al cliente.<br>- El sistema genera un `accountId` para identificar la cuenta.<br>- La cuenta queda registrada con su balance y estado correspondiente.<br>- La información queda almacenada únicamente en la base de datos de Account Service.<br>- El sistema confirma que la cuenta fue creada correctamente. |
| **Escenario Principal** | 1. El Cajero Receptor selecciona la opción **Crear cuenta bancaria**.<br>2. El sistema muestra el formulario para crear una nueva cuenta.<br>3. El Cajero Receptor selecciona o ingresa el cliente mediante su `customerId`.<br>4. El Cajero Receptor selecciona el tipo de cuenta: **Monetaria** o **Ahorro**.<br>5. El Cajero Receptor ingresa el balance inicial correspondiente.<br>6. El sistema valida la información proporcionada.<br>7. El sistema genera un `accountId` para la nueva cuenta.<br>8. El sistema establece el estado inicial de la cuenta.<br>9. El sistema almacena la información en la base de datos de Account Service.<br>10. El sistema informa que la cuenta bancaria fue creada correctamente. |
| **Escenario Alternativo** | **1. Cliente no válido:** Si el `customerId` proporcionado no es válido, el sistema rechaza la creación de la cuenta e informa el error.<br><br>**2. Tipo de cuenta no seleccionado:** Si no se selecciona entre cuenta Monetaria o Ahorro, el sistema solicita completar este campo antes de continuar.<br><br>**3. Balance inicial inválido:** Si el valor ingresado para el balance no cumple con las reglas establecidas, el sistema solicita corregirlo.<br><br>**4. Datos incompletos:** Si falta información obligatoria, el sistema indica los campos que deben completarse.<br><br>**5. Error durante la creación:** Si ocurre un fallo durante el proceso, el sistema evita almacenar información incompleta y notifica al usuario. |
| **Requerimientos** | - El sistema debe permitir crear una cuenta bancaria para un cliente registrado.<br>- Cada cuenta debe contar con un identificador único `accountId`.<br>- La cuenta debe estar asociada a un `customerId`.<br>- El sistema debe manejar los tipos de cuenta **Monetaria** y **Ahorro**.<br>- El sistema debe almacenar el balance y estado de la cuenta.<br>- La información de la cuenta debe almacenarse únicamente en la base de datos correspondiente a Account Service.<br>- Account Service no debe acceder directamente a la base de datos de Customer Service.<br>- La comunicación entre microservicios debe realizarse de manera asíncrona mediante eventos.<br>- El proceso debe contemplar manejo de errores y evitar la duplicidad de operaciones. |

### Caso de Uso: Realizar transferencia entre cuentas

| Campo | Descripción |
|---|---|
| **ID Caso de Uso** | CDU-TRX-01 |
| **Nombre** | Realizar transferencia entre cuentas |
| **Módulo al que pertenece** | Transaction Service |
| **Actor Principal** | Cliente |
| **Precondiciones** | - El cliente debe haber iniciado sesión correctamente.<br>- El cliente debe contar con una cuenta bancaria válida.<br>- La cuenta origen y la cuenta destino deben existir.<br>- El cliente debe indicar el monto que desea transferir.<br>- La cuenta origen debe disponer de fondos suficientes para realizar la operación. |
| **Postcondiciones** | - Se registra una nueva transacción con un `transactionId` único.<br>- La transacción queda asociada a la cuenta origen y a la cuenta destino.<br>- Se registra el monto y el estado de la transacción.<br>- Si la transferencia finaliza correctamente, se actualizan los balances correspondientes mediante el flujo distribuido.<br>- El sistema conserva la trazabilidad de la operación mediante un `correlationId`. |
| **Escenario Principal** | 1. El cliente selecciona la opción **Realizar transferencia**.<br>2. El sistema solicita la cuenta origen, la cuenta destino y el monto a transferir.<br>3. El cliente ingresa los datos solicitados y confirma la transferencia.<br>4. El Transaction Service recibe la solicitud de la operación.<br>5. El sistema genera un `transactionId` y un `correlationId` para identificar y rastrear la operación.<br>6. El sistema inicia el flujo distribuido de transferencia mediante eventos asíncronos.<br>7. Se valida que la cuenta origen disponga de fondos suficientes.<br>8. Si la validación es correcta, se continúa con la actualización de los balances correspondientes.<br>9. Transaction Service registra la transacción con los datos de la cuenta origen, cuenta destino, monto y estado.<br>10. El sistema marca la transacción como completada cuando finaliza correctamente el flujo.<br>11. Se publica el evento correspondiente para que otros servicios puedan reaccionar, por ejemplo, para generar una notificación.<br>12. El sistema informa al cliente que la transferencia fue realizada correctamente. |
| **Escenario Alternativo** | **1. Fondos insuficientes:** Si la cuenta origen no posee fondos suficientes, la transferencia es rechazada y se registra el estado correspondiente.<br><br>**2. Cuenta origen inválida:** Si la cuenta origen no puede ser validada, el sistema cancela la transferencia.<br><br>**3. Cuenta destino inválida:** Si la cuenta destino no puede ser validada, el sistema cancela la operación e informa el error.<br><br>**4. Monto inválido:** Si el monto ingresado no es válido, el sistema no inicia la transferencia y solicita corregirlo.<br><br>**5. Fallo durante el flujo distribuido:** Si ocurre un error después de haber iniciado la transferencia, el sistema debe ejecutar los eventos de compensación definidos mediante el patrón Saga para evitar inconsistencias.<br><br>**6. Evento duplicado:** Si el sistema recibe nuevamente un evento ya procesado, debe aplicar idempotencia para evitar ejecutar dos veces la misma operación.<br><br>**7. Fallo temporal:** Si ocurre un fallo recuperable durante el procesamiento, el sistema puede aplicar reintentos (`retries`) sin duplicar la transacción. |
| **Requerimientos** | - Transaction Service debe permitir realizar transferencias entre cuentas.<br>- El sistema debe validar la disponibilidad de fondos antes de completar la transferencia.<br>- Cada transacción debe contar con un identificador único `transactionId`.<br>- La transacción debe registrar `sourceAccount`, `targetAccount`, `amount` y `status`.<br>- El flujo debe utilizar un `correlationId` para permitir la trazabilidad de la operación.<br>- La comunicación entre microservicios debe ser completamente asíncrona mediante el broker de mensajería.<br>- Transaction Service no debe acceder directamente a las bases de datos de otros microservicios.<br>- El flujo de transferencia debe implementar el patrón Saga.<br>- Deben contemplarse eventos de compensación ante fallos.<br>- El procesamiento debe manejar `retries` e idempotencia para garantizar que una transacción no se procese más de una vez. |

### Caso de Uso: Enviar Notificacion

| Campo | Descripción |
|---|---|
| **ID Caso de Uso** | CDU-NOT-01 |
| **Nombre** | Enviar notificación |
| **Módulo al que pertenece** | Notification & Audit Service |
| **Actor Principal** | Sistema |
| **Precondiciones** | - Debe haberse generado un evento que requiera notificar al usuario.<br>- El evento debe haber sido publicado en el broker de mensajería.<br>- Notification & Audit Service debe estar disponible para consumir el evento.<br>- El evento debe contener la información necesaria para identificar el tipo de notificación y sus datos asociados. |
| **Postcondiciones** | - El evento recibido queda procesado por Notification & Audit Service.<br>- Se genera la notificación correspondiente.<br>- El sistema registra la información necesaria para auditoría.<br>- El evento queda registrado con sus datos asociados, como `eventId`, `tipoEvento`, `timestamp` y `payload`.<br>- El procesamiento de la notificación no modifica directamente la lógica de negocio de otros microservicios. |
| **Escenario Principal** | 1. Un microservicio genera un evento como resultado de una operación del sistema.<br>2. El evento es publicado de forma asíncrona en el broker de mensajería.<br>3. Notification & Audit Service consume el evento publicado.<br>4. El servicio identifica el tipo de evento recibido.<br>5. El sistema obtiene la información necesaria del `payload` del evento.<br>6. El sistema genera la notificación correspondiente.<br>7. La notificación es enviada al usuario según el evento procesado.<br>8. El sistema registra el evento para fines de auditoría.<br>9. Se almacena el `eventId`, `tipoEvento`, `timestamp` y `payload` correspondiente.<br>10. El proceso finaliza sin afectar directamente la lógica de negocio del microservicio que originó el evento. |
| **Escenario Alternativo** | **1. Evento inválido:** Si el evento recibido no contiene la información necesaria, el sistema no genera la notificación y registra el error.<br><br>**2. Tipo de evento no reconocido:** Si `tipoEvento` no corresponde a un evento soportado, el sistema registra el evento para auditoría pero no genera una notificación.<br><br>**3. Error al enviar la notificación:** Si ocurre un fallo durante el envío, el sistema registra el error para su seguimiento.<br><br>**4. Evento duplicado:** Si se recibe nuevamente un evento que ya fue procesado, el sistema debe evitar generar una notificación duplicada mediante mecanismos de idempotencia.<br><br>**5. Fallo temporal del servicio:** Si Notification & Audit Service no puede procesar temporalmente el evento, este debe poder ser procesado posteriormente según el mecanismo de mensajería utilizado. |
| **Requerimientos** | - Notification & Audit Service debe permitir el envío de notificaciones a partir de eventos del sistema.<br>- El servicio debe registrar eventos para fines de auditoría.<br>- Cada evento debe manejar un `eventId`.<br>- El sistema debe registrar `tipoEvento`, `timestamp` y `payload`.<br>- La comunicación con los demás microservicios debe realizarse de manera asíncrona mediante eventos.<br>- Notification & Audit Service no debe acceder directamente a las bases de datos de otros microservicios.<br>- El servicio debe mantenerse desacoplado de la lógica de negocio de los demás componentes.<br>- El sistema debe contemplar manejo de errores durante el procesamiento de eventos.<br>- El procesamiento debe evitar notificaciones duplicadas cuando se reciba nuevamente un mismo evento. |
